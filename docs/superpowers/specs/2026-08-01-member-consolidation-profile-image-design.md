# Member 단일화 + 프로필 이미지 설계

- 작성일: 2026-08-01
- 대상: `app-mvc` auth 도메인, `app-mvc` blog 도메인(정합), `front` auth 호출부
- 전신 참조: `/Users/administrator/Documents/projects/art-market-place` 의 product/blog 이미지 업로드 구현

## 배경

`auth` 도메인은 회원을 `Buyer` / `Seller` 두 엔티티(`buyers` / `sellers` 두 테이블)로 나눠 갖고 있다.
전신 레포의 art-marketplace 도메인(구매자·판매자 거래)에서 온 구분인데, product/cart 도메인을 폐기한
현 구조에서는 두 유형을 나눌 근거가 남아 있지 않다. 역할 구분은 토큰의 `role`(`ROLE_BUYER` /
`ROLE_SELLER`)과 blog의 `(member_id, member_role)` 작성자 식별자까지 번져 있다.

동시에 회원에게 프로필 이미지가 필요하다. 전신 레포에는 이미 두 가지 이미지 업로드 구현이 있다:

- **product 패턴** (`ProductImageStorageService`): presigned PUT URL 발급 → 클라이언트가 S3에 직접
  업로드(`temp/products/...`) → fileKey 등록 → 커밋 후 이벤트로 `products/{id}/...` 로 copy+delete,
  실패 시 보상 삭제. 조회는 presigned GET URL.
- **blog 패턴** (`PostServiceImpl`): `MultipartFile` 을 서버가 받아 `s3Client.putObject` 로 업로드.

S3/MinIO 배선(`S3Client`, `S3Presigner`, `storage.s3.*`)은 이미 `app-mvc` 의
`_common/storage` 에 이관돼 있다. 즉 새로 만들 것은 배선이 아니라 프로필 이미지 도메인 로직이다.

## 목표

1. `Buyer` / `Seller` 를 단일 `Member` 로 통합한다. 필드는 기존 `Buyer` 와 동일하게 두고,
   `Seller` 고유 필드 `businessRegistrationCertificateUrl` 은 버린다.
2. `Member` 에 프로필 이미지와 보유 게임 머니를 추가한다.
3. 프로필 이미지는 presigned PUT 업로드 / presigned GET 조회로 제공한다.

## 비목표

- 게임 머니 증감 API. 게임 규칙·실시간 통신 방식이 후속 spec으로 남아 있어, 잔액을 움직이는 계약은
  그 spec에서 정한다. **이번 변경 후 `gameMoney` 는 항상 0이다.**
- 프로필 이미지 프론트엔드 UI. 백엔드 계약만 만든다.
- `front` 의 `app/products`, `app/cart`, `app/chat`. 이미 폐기된 백엔드를 호출하는 별도 후속 과제다.
- blog의 QueryDSL 잔존(`PostQueryRepositoryImpl`) 네이티브 SQL 전환.

## 결정 사항

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 업로드 방식 | presigned PUT 2-step (product 패턴) | 파일 바이트가 앱을 경유하지 않는다 |
| 조회 방식 | presigned GET URL | 버킷을 private로 유지하며 기존 product/blog와 동일 |
| 저장 위치 | `members.profile_image_key` 컬럼 | 회원당 프로필 1장 = 컬럼 1개. 조인·N+1 없음 |
| 스키마 이관 | `V1__auth_blog.sql` 직수정 + 로컬 DB 재초기화 | 마이그레이션을 하나로 유지. 보존할 개발 데이터가 없다 |
| role 계약 | `ROLE_MEMBER` 단일, blog `member_role` 제거 | 상수값 컬럼을 남기지 않는다 |
| temp 단계 | 없음. 최종 키로 직접 업로드 | 회원이 이미 존재해 최종 키를 처음부터 알 수 있다 |
| front 범위 | auth 호출부만 정합 | signup 엔드포인트 변경으로 깨지는 부분까지 |

## 설계

### 1. Member 통합

**엔티티** — `auth/entity/Member` (`members` 테이블). 필드:

```
id, googleSubject, email, nickname, termsAgreed, privacyPolicyAgreed,
profileImageKey (nullable), gameMoney (long, 기본 0), active, createdAt
```

`Member.create(googleSubject, email, nickname, termsAgreed, privacyPolicyAgreed)` 가
`active=true`, `gameMoney=0`, `profileImageKey=null` 로 생성한다.

삭제: `Buyer`, `Seller`, `MemberType`, `BuyerRepository`, `SellerRepository`.
신규: `MemberRepository` (`findByEmail`, `findByGoogleSubject`, `existsByGoogleSubject` — 모두 단일
컬럼 조회이므로 Spring Data 파생 메서드).

`Address` 는 `member_id` 로 회원을 가리키던 의미가 그대로여서 손대지 않는다.

**스키마** — `V1__auth_blog.sql` 에서 `buyers` / `sellers` 두 CREATE를 `members` 하나로 교체한다.

```sql
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    google_subject VARCHAR(100) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    nickname VARCHAR(60) NOT NULL,
    terms_agreed BOOLEAN NOT NULL,
    privacy_policy_agreed BOOLEAN NOT NULL,
    profile_image_key VARCHAR(1000),
    game_money BIGINT NOT NULL DEFAULT 0,
    active BOOLEAN NOT NULL,
    created_at TIMESTAMP(6) NOT NULL
);
```

`posts` / `comments` / `likes` 에서 `member_role` 컬럼을 제거하고,
`uk_likes_member_post` 를 `(member_id, post_id)`, `idx_posts_member` 를 `(member_id)` 로 축소한다.

V1을 직수정하므로 **이미 적용된 로컬 DB는 Flyway checksum 불일치로 부팅에 실패한다.** 적용 시
로컬 postgres 볼륨을 초기화한다.

**API** — `POST /api/auth/signup/buyers` + `/signup/sellers` → **`POST /api/auth/signup`** 하나.

- 신규 `MemberSignupRequest(nickname, termsAgreed, privacyPolicyAgreed, device)`.
  기존 `BuyerSignupRequest` / `SellerSignupRequest` 삭제.
- `LoginRequest` 에서 `memberType` 제거 → 로그인은 google subject로 회원을 찾는다.
- `GoogleAuthorizationAction` 은 `SIGNUP`, `LOGIN` 2개.
- `GoogleAuthorizationContext` 에서 `memberType`, `businessRegistrationCertificateUrl` 제거.

**토큰** — role은 `"ROLE_MEMBER"` 상수 하나. Redis의 `role` 값은 자유 문자열이고 `app-webflux` 는
값을 검증 없이 전달만 하므로(`ReactiveTokenVerifier` → `GamePrincipal`), `core` 의 토큰 계약
(`AuthTokenType`, `TokenMetadata`)은 바뀌지 않는다. `AuthTokenTypeTest` 는 무변경으로 통과해야 한다.

`AccessTokenLoginIdHeaderFilter` 의 role 분기가 사라지고 `MemberRepository.findById → email` 로 축소된다.

**blog 정합** — `Posts` / `Comments` / `Likes` 의 `memberRole` 필드, `LikeRepository` 의
`existsByMemberIdAndMemberRoleAndPostId` / `findByMemberIdAndMemberRoleAndPostId` 파생 메서드,
`AuthMemberResolver` 의 role 분기와 `MemberIdentity.role` 을 제거한다. 호출부는
`PostServiceImpl`(작성·수정 권한 검사·좋아요 여부), `CommentServiceImpl`(작성·수정 권한 검사·작성자
loginId 조회), `LikeServiceImpl`(등록·해제). 작성자 동일성 검사는 `memberId` 비교만 남는다.
`AuthMemberResolver.resolveLoginId(memberId)` 는 `memberRole` 인자를 잃는다.

### 2. 프로필 이미지

**키 규칙** — `profiles/{memberId}/{uuid}/{sanitized-filename}`. temp 경유 없음. 교체 시 새 uuid
디렉토리로 올리고 이전 키를 삭제하므로 키 충돌이 없다.

**서비스** — `auth/service/MemberProfileImageService`.

전신 `ProductImageStorageService` 에서 **가져오는 것**: presign PUT / presign GET 구성,
`sanitizeFileName`(경로 구분자 제거 + 화이트리스트 치환), 실패를 로그로 흘리는 삭제.

**버리는 것**: `temp → 최종` copy+delete, `toProductFileKey`, `validateTempProductFileKey`,
`ProductImagesRegisteredEvent` + `TransactionalEventListener` 보상 로직. 회원이 이미 존재해
최종 키를 바로 알 수 있으므로 전부 불필요하다.

S3 배선은 기존 `_common/storage` 의 `S3Client` / `S3Presigner` / `StorageProperties` 를 주입받는다.
서비스는 `_common` 이 아니라 `auth` 에 둔다 — 프로필은 auth 도메인 로직이다.

**엔드포인트** — `/api/auth`. 인증은 `AccessTokenLoginIdHeaderFilter` 가 주입하는 `loginId` 헤더로
하고, 없으면 `401` 이다.

| 기능 | 메서드 · 경로 | 요청 → 응답 |
| --- | --- | --- |
| 업로드 URL 발급 | `POST /me/profile-image/presigned-url` | `{fileName, contentType}` → `{uploadUrl, fileKey, expiresInSeconds}` |
| 등록/교체 | `PUT /me/profile-image` | `{fileKey}` → `{profileImageUrl}` |
| 삭제 | `DELETE /me/profile-image` | — → `204` |
| 내 프로필 조회 | `GET /me` | — → `{memberId, email, nickname, gameMoney, profileImageUrl}` |

`profileImageUrl` 은 presigned GET URL이고, 미설정이면 `null` 이다.

**서버가 실제 파일 바이트를 보지 못하는 방식이므로 두 가지 검증을 product 패턴에 더한다:**

1. **contentType 화이트리스트** — `image/png`, `image/jpeg`, `image/webp`, `image/gif` 만 발급한다.
   그 밖은 `400`.
2. **fileKey prefix 검증** — 등록 시 fileKey가 `profiles/{요청자 memberId}/` 로 시작하는지 확인한다.
   그 밖은 `403`. 이 검증이 없으면 임의 오브젝트 키를 남의 프로필로 붙일 수 있다.

발급 시 키의 `memberId` 는 요청 본문이 아니라 **서버가 토큰에서** 결정한다.

**등록/교체 순서** — 새 키를 컬럼에 쓰고(트랜잭션 커밋) 그 다음 이전 오브젝트를 삭제한다. 삭제가
실패해도 프로필은 정상이며 고아 오브젝트만 남는다(로그 경고).

**고아 오브젝트** — 발급받고 등록하지 않은 업로드는 `profiles/` 하위에 남는다. 이번 범위에서는
정리하지 않는다. 버킷 lifecycle 정책이나 별도 정리 작업은 후속 과제로 둔다.

### 3. front 정합 (auth 호출부만)

- `front/lib/api.ts`: `signup/buyers` · `signup/sellers` 두 함수를 `/api/auth/signup` 하나로 합치고,
  `startGoogleLogin(memberType)` → `startGoogleLogin()`.
- `front/lib/types.ts`: auth 관련 타입에서 `MemberType` 제거. product/cart 타입의
  `sellerId` / `buyerId` 는 폐기된 백엔드용이므로 손대지 않는다.
- 페이지: `app/signup/page.tsx`(구매자/판매자 선택)를 단일 가입 폼으로 바꾸고
  `app/signup/buyer` · `app/signup/seller` 를 삭제. `app/login/page.tsx`,
  `components/auth/signup-form.tsx`, `components/auth/google-auth-button.tsx`,
  `components/header.tsx` 에서 역할 분기 제거.
- 검증: `npm run build`.

### 4. 게임 머니

`members.game_money BIGINT NOT NULL DEFAULT 0` / `Member.gameMoney` (`long`). 가입 시 0으로
생성하고 `GET /api/auth/me` 응답에 노출한다. 증감 경로는 만들지 않는다.

기록해 둘 점: 이후 `app-webflux` 가 이 잔액을 R2DBC로 읽으면 `members` 는 두 앱이 공유하는 첫
테이블이 된다. 스키마 단일 소스는 그대로 `app-mvc` Flyway이지만, game spec에서 잔액의 쓰기 소유권을
명시해야 한다.

## 테스트

`docs/auth/PRD.md` 의 AC 표를 먼저 갱신하고 테스트를 맞춘다.

기존 AC 수정:

- `AUTH-AC-08` — "구매자/판매자 회원가입이 성공하면 해당 엔티티를 `active=true` 로 생성한다"
  → "회원가입이 성공하면 `members` 에 `active=true`, `gameMoney=0` 으로 생성한다"

신규 AC:

| ID | 인수 기준 (Given–When–Then) | 커버 테스트 |
| --- | --- | --- |
| AUTH-AC-09 | 로그인은 memberType 없이 google subject로 회원을 찾고, 미등록이면 `404` 를 반환한다 | `AuthServiceTest` |
| AUTH-AC-10 | presigned 발급은 `profiles/{요청자 memberId}/` prefix 키와 TTL을 반환한다 | `MemberProfileImageServiceTest` |
| AUTH-AC-11 | 허용 목록 밖 contentType으로 발급을 요청하면 `400` 을 반환한다 | `MemberProfileImageServiceTest` |
| AUTH-AC-12 | 다른 회원 prefix의 fileKey를 등록하면 `403` 을 반환한다 | `MemberProfileImageServiceTest` |
| AUTH-AC-13 | 교체가 성공하면 컬럼을 갱신하고 이전 오브젝트를 삭제한다 | `MemberProfileImageServiceTest` |
| AUTH-AC-14 | `GET /me` 는 presigned GET URL을 반환하고, 프로필 미설정이면 `null` 을 반환한다 | `MemberProfileImageControllerTest` |

- S3 호출은 `S3Client` / `S3Presigner` 목으로 검증한다. MinIO 기동에 의존하지 않는다.
- 기존 `AuthServiceTest`, `AuthControllerTest`, `TokenGenerateControllerTest`,
  `WoobeeeMvcApplicationTests` 의 Buyer/Seller 픽스처를 `Member` 로 재작성한다.
- `SchemaValidationTest` 는 V1 수정과 엔티티 변경이 맞물려야 통과한다(실 PostgreSQL 필요).
- `AuthTokenTypeTest` 는 계약 무변경이므로 그대로 통과해야 한다.
